## D8 · SSE 认证走 Cookie（方案 B）

`EventSource` 不能自定义请求头，所以 SSE 只能靠 Cookie 认证。决定 **APK 也统一走 Cookie**。

影响与待办：

- APK 的 WebView 必须能在**长连接**下稳定携带 `SameSite=None; Secure` 的 Cookie ——
  现有配置已经是这样（`app/settings.py`），但要在真机上验长连接场景
- Bearer token 那条路（`app/mobile/session_service.py`）**不删**，REST 继续支持，
  只是 SSE 不用它
- Cookie 的 `path` 要等于 `APP_BASE_PATH`（见 [11](11-BASE_PATH.md) §5），
  否则多项目共域名时会互相踢下线
- 好处：URL 里不出现 token，nginx 日志不会泄露凭证

> ⚠️ 验收硬门槛：**真机 APK 上开一条 SSE 挂机 30 分钟，中途锁屏解锁，Cookie 仍有效。**
> 不通过就得退回方案 C（fetch + ReadableStream 自己解析）。

## D10 · `{BASE}` = `/UTBA_DEMO`（大写）

已确认用大写。`APP_BASE_PATH` 是 `system_config.env` 的每环境配置，代码不写死。

必须配套做（否则手打小写就 404）：

```nginx
location ~* ^/utba_demo(/.*)?$ { return 301 /UTBA_DEMO$1; }
```

规范写法只有一个（`/UTBA_DEMO`），其余一律 301 过去，避免同一页面两个 URL。

## D11 · 技术参数（实测 2026-09-23）

### 1. 数据库连接上限 ★ 有冲突

```
MariaDB 11.4.10   max_connections = 151   当前连接 12
```

**4 个 uvicorn worker × 默认线程池 40 = 160 > 151。**
按默认配置上线会连接耗尽。必须显式限制：

```python
# core/db.py
engine = create_engine(uri, pool_size=8, max_overflow=4, pool_pre_ping=True, pool_recycle=280)
# 4 worker × (8+4) = 48 条，留足余量给其他 5 个共用同一实例的项目
```

同时把 uvicorn 的线程池调小（`anyio` 默认 40 太大）：每 worker 12–16 即可。

> ⚠️ 迁到 PG 后这条更紧：**PG 默认 `max_connections = 100`**，比 MariaDB 还小。
> 见 [15](15-PostgreSQL迁移.md) §6。

### 2. 最长请求耗时 —— 测不到，需先埋点

nginx 当前的 `log_format` **没有记 `$request_time`**，access.log 里查不到。
**动手前先加**（改完立刻能积累数据，零风险）：

```nginx
log_format timed '$remote_addr - $remote_user [$time_local] "$request" '
                 '$status $body_bytes_sent "$http_referer" "$http_user_agent" '
                 'rt=$request_time urt=$upstream_response_time';
access_log /var/log/nginx/access.log timed;
```

积累一两周后取 p99 与最大值，据此定 worker 的 `--timeout`。
凭经验，嫌疑最大的是：视频转码触发接口、批量牌位 PDF、AI 读单、批量下载 zip。

### 3. nginx HTTP/2 ★ 未启用 —— SSE 的拦路石

实测：`nginx/1.24.0`，所有 server 块都是 `listen 443 ssl;`，**没有 http2**。

这意味着现在上 SSE 会直接撞上"浏览器每域名 6 连接"的上限
（见 [12](12-SSE改造方案.md) §5 坑 1）。**必须先开**。

注意 1.24 用的是旧语法（`http2 on;` 是 1.25.1+ 才有的）：

```nginx
listen 443 ssl http2;       # nginx 1.24 的写法
```

- [ ] 开启后用 DevTools 确认 Protocol 列是 `h2`
- [ ] 这是**独立于迁移的改动**，可以现在就做

### 5. SSE 并发连接峰值 —— 估算

无历史数据可查。按业务形态估：

| 场景 | 估算并发 SSE |
|---|---|
| 平日 | < 10 |
| 活动/共修当天 | 20–50 |
| **法会当天**（多个终端 + 义工手机 + 公开页） | **100–200** |

一条 SSE 连接 ≈ 一个 asyncio 任务（几 KB），200 条对单进程毫无压力。
**真正的瓶颈是快照查询占用的线程池**（见 [12](12-SSE改造方案.md) §5 坑 3）——
所以 snapshot 必须快，必要时加 Redis 缓存。

- [ ] 上线后监控实际峰值，据此调 worker 数与线程池

## D12 · 工期评估（我的判断）

加入 D9 的 R3 与 D14 的 PG 迁移后，范围变大了。老实估：

| 阶段 | 内容 | 全职估时 |
|---|---|---|
| **P0** | **PG 迁移（在现有 Flask 上先做）** | **2–3 周** |
| 1 | 地基：配置 + 路径 + 骨架 + 垫片 + SSE 基础设施 | 2–3 周 |
| 2 | REST 重写 **+ R3 路径规范化** | 6–11 周 |
| 3 | 实时改造（POST + SSE + 前端 21 个文件） | 2–3 周 |
| 4 | 验收演练 | 1–2 周 |
| 5 | 切换 | 1 天 |
| **合计** | | **13–22 周全职** |

非全职（晚上 + 周末）按 **2.5–3 倍**估：**8–16 个月**。

### 我的三条建议

**1. PG 迁移排在最前面，而且单独切一次。**
不要和框架迁移捆在一起 —— 同时换框架又换数据库，出问题时无法判断是哪个引起的。
先在**现有 Flask 代码上**迁到 PG，用已知正确的行为验证 PG 侧无误；
之后 FastAPI 迁移就没有数据库这个变量了。两次停机窗口换来的是可归因性，值得。

**2. R3 不要单独排期，必须和阶段 2 揉在一起。**
同一个路由文件改两遍是纯浪费。

**3. 给"法会/点灯/报名"这些硬日历留出禁改期。**
排期时先把这些日子标成红区，**红区前两周冻结上线**。
这不是保守，是这个系统的业务性质决定的。

## D13 · 配置：不动 `_token.py`，直接复制值

`/srv/flaskapp/_token.py` 被 6 个项目共用，改它会波及别人。决定：

- **不碰**那个文件，也不做"回落到旧来源"的兼容逻辑（原计划里的那一步取消）
- 把它的 17 个键 + `.flaskenv` 的 10 个键，**一次性复制进** `system_config.env`
- 仓库里的 `_token.py` 在迁移完成后**直接删除**
- 两边从此各走各的：别的项目继续用共享文件，本项目只认 `system_config.env`

好处：配置来源唯一、可测试、启动即校验。代价：**共享值（如 DB 密码）以后改动要改两处** ——
这是可接受的，因为本项目马上要迁到独立的 PG 库（D14），共享面会自然消失。

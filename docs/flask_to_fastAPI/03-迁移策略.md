# 03 · 迁移策略：一步到位

## 0. 前提已定（2026-09-23 确认）

| 约束 | 决定 | 对计划的影响 |
|---|---|---|
| 迁移动机 | **全面支持 SSE 长连接** | 这是 FastAPI 真正的理由，见 §1 |
| Socket.IO | **全面下线并移除** | 35 个事件全改，见 [12](12-SSE改造方案.md) |
| 停机 | **可以停机更新** | 不需要绞杀榕、不需要灰度并存；PG 与 FastAPI **各切一次** |
| 遗留 | **不留任何 Flask** | 一次性重写，不做双栈 |
| 旧链接 / 旧二维码 | **不需要保留** | 契约可以改，URL 可以变 |
| 数据库 | **迁 PostgreSQL** | 团队更熟悉 PG；见 [15](15-PostgreSQL迁移.md) |
| REST 契约 | **全面规范化（R0–R3）** | 见 [13](13-API重新设计.md)，与重写同一次做完 |

→ 原先的「绞杀榕 + 契约冻结 + 3–6 个月」方案作废，改为**一次性重写 + 停机切换**。

## 1. 为什么这次 FastAPI 是对的选择

之前的版本里我写过「FastAPI 不会让这个项目变快」—— 那个结论在**纯 REST** 前提下成立，
但**动机是 SSE，情况完全不同**：

| | Flask（WSGI, gunicorn sync） | FastAPI（ASGI, uvicorn） |
|---|---|---|
| 一条 SSE 长连接占用 | **一个 worker 进程/线程** | 一个 asyncio 任务（几 KB） |
| 100 个并发 SSE | 需要 100 个 worker —— 不可行 | 一个 worker 轻松扛住 |
| 长连接期间能否处理别的请求 | 不能（sync worker 被占住） | 能 |

WSGI 下做 SSE 只能靠 eventlet/gevent 打猴子补丁（也就是现在 socket.io 那个进程在做的事），
而猴子补丁与 Python 新版本的兼容性在持续恶化。**ASGI 是长连接的正路。**

所以这次迁移的收益是实打实的：
- SSE 从"勉强能跑"变成"原生支持"
- 干掉 eventlet 猴子补丁这个长期技术债
- 少一个进程、少一套 socket.io 协议栈、前端少一个依赖
- 顺带拿到类型校验与 OpenAPI

## 2. 为什么"一步到位"可行（以及它的真实代价）

可行，因为三个前提同时成立：**能停机 + 不留旧契约 + 有独立 dev 环境**。

但要认清代价：

> **一步到位 = 在全部做完之前，什么都不能上线。**
> 中间没有"做完一半也有收益"的节点，只有一次性的成败。

唯一的缓解手段是：**dev 域名（`yukang.utbabuddha.com` → :5102）从第一天起就跑新栈**，
每天可用、每天自测。这不是"灰度"，而是让"全部做完"这件事有连续的可见进度，
而不是三个月后第一次启动。

- [ ] **规则：新栈必须每天能在 dev 域名上起来。** 连续两天起不来就是红灯，停下来修。

## 3. 总体形态

```
                       ┌──────────────────────────────────────────┐
                       │  asgi.py   FastAPI + uvicorn             │
 nginx ────────────────┤                                          │
 （HTTP/2 必开）        │   {BASE}/api/{app}/realtime  ← SSE 统一入口│
                       │   {BASE}/api/...             ← REST      │
                       │   {BASE}/...                 ← 公开页/短链 │
                       └──────────────────────────────────────────┘
                                 Redis（pub/sub 扇出 + 房间态 + 缓存）
                                 MySQL（pymysql，模型完全不变）

  删除：xinya_socket.service、eventlet、flask-socketio、socket.io-client
```

**进程从 2 个变 1 个。** 这是本次迁移最直观的结构收益。

## 4. 阶段划分

| 阶段 | 名称 | 内容 | 估时（全职） |
|---|---|---|---|
| **0** | 解耦小事 | nginx 开 HTTP/2、日志加 `$request_time`、大小写 301 | 半天 |
| **P0** | **PG 迁移** | **在现有 Flask 上**迁到 PostgreSQL，单独切一次 | 2–3 周 |
| **1** | 地基 | 配置中心 + 路径基座 + FastAPI 骨架 + 三层垫片 + SSE 基础设施 | 2–3 周 |
| **2** | REST 重写 **+ R3** | 505 个函数搬完，同时完成路径规范化 | 6–11 周 |
| **3** | 实时改造 | 22 个动作改 POST + 23 种广播改 SSE + 前端 21 个文件 | 2–3 周 |
| **4** | 验收演练 | 全功能走查 + 压测 + 停机演练 | 1–2 周 |
| **5** | 切换 | 停机窗口内切换 + 观察 | 1 天 |

**合计 13–22 周全职**（非全职按 2.5–3 倍 → 8–16 个月）。评估依据见 [09](09-待决事项.md) §D12。

⚠️ **阶段 0 现在就能做**，尤其 HTTP/2 —— 实测未开，是 SSE 的拦路石。
⚠️ **P0 与阶段 1–5 各切一次机**。同时换框架又换数据库，出问题时无法归因。

阶段 1 与 2 有重叠（地基完成后就能并行搬模块）；阶段 3 依赖阶段 2 对应模块搬完。

## 5. 契约变更范围（D9：全面规范化）

| 项 | 建议 | 理由 |
|---|---|---|
| REST 路径（`/api/xxx`） | **改**成 `/api/v1/{resource}`（D9 已定做 R3） | 代价是前端 400 处调用跟着改；换来 MCP 与 OpenAPI 可用 |
| 响应体形状（`{"status":"success"}`） | **保持不变** | 同上；而且垫片能让后端零成本保持 |
| 实时通道 | **改**，统一到 `/{app}/realtime` | 这是本次迁移的目的本身 |
| 路径前缀 | **改**，加 `{BASE}` | 多项目部署的需求，见 [11](11-BASE_PATH.md) |
| `abort()` 的 HTML 错误页 | **改**成 JSON | 本来就该是 JSON |
| 双下划线怪路径（如 `/api/api/get_event`） | **改** | 随 R3 一起 |

→ 决策见 [09](09-待决事项.md) D9，方案见 [13](13-API重新设计.md) §3。

## 6. ★ APK 必须先加"最低版本门禁"

**这是切换前唯一不能省的前置工作。**

现状：`app/app_release/` 只提供 APK 下载，**没有版本校验**。停机切换后：

> 用户手机上的旧 APK 会继续打老接口 → 全部 404 → **白屏或满屏报错，
> 用户不知道发生了什么，只会以为"系统坏了"。**

所以切换前必须先发一个**过渡版 APK**：

1. 新增 `GET /api/app/min_version` 返回最低可用版本
2. APK 启动时检查，低于最低版本就显示**全屏提示 + 下载按钮**，不进主界面
3. 这个过渡版本要**提前至少 2–4 周发布**，并盯着升级率
4. 切换当天把 `min_version` 提到新版本号

- [ ] 没做完这一步，**不许进入停机切换**。

## 6.5 为什么不推倒重写（一个被问过的问题）

"这个量级是不是重写后台更理想？" —— 先把"重写什么"量化清楚：

| 层 | 行数 | 占比 | 本计划怎么处理 |
|---|---:|---:|---|
| 路由层 `routes.py` | 7,899 | 19% | **全部重写**（这就是 FastAPI 迁移） |
| 业务层 `services.py` | 15,682 | 38% | 垫片保留，**逐字不动** |
| 数据层 `models/` | 4,702 | 11% | 垫片保留，**逐字不动** |
| 其余（PDF/OCR/AI/工具） | 13,249 | 32% | 基本不动 |

**本计划已经是一次重写 —— 重写的是那 19%。** 真正的问题是：要不要连另外 81% 一起扔掉。

### 答案是不要，理由是这个代码库特有的

**1. 这不是薄 CRUD。** 23 个模块里只有 `public_api` 一个是薄 CRUD（20 行/路由），
其余全部在 35–180 行/路由之间 —— 几乎每个接口背后都有真实业务逻辑。

**2. 没有测试、没有规格书 → 代码本身就是唯一的规格。**
仅中文注释里就有 50 处记录着别处查不到的规则，例如：

- `同一个人挂多个关系（例如 曹振华 既是「亡夫」又是「亡父」）` —— 牌位重名处理
- `同一列的格心在 point.json 里会差个一两点（例如 paiwei_10 的 292 / 293）` —— 板位坐标的经验校准
- `历史版本的订单一律只读：只能查看，或「复制到今年」后再修改`
- `去重同样要认各种写法，否则同一个人换个格式提交就会被当成新客人`
- `全局年龄规则：只按出生年份计算，不看月份/生日`
- 旧式 IC（7–8 位纯数字）推不出生日，30 位老会员属于此类

这些是几年里被真实用户撞出来的边界情况。**重写会把它们全部丢掉，
然后一个一个地由用户在生产环境替你重新发现。**

**3. 失败模式很具体。** 这个系统服务的是有**固定日历**的业务 ——
盂兰盆法会、点灯、青少年班报名每年准时到来。
一个"完成度 80%"的重写在法会当天价值为零，而旧系统在重写期间还得继续维护，
等于同时养两套。

**4. 成本不是"差不多"，是数量级差异。**

| | 工期 | 风险 |
|---|---|---|
| 移植（本计划） | 9–16 周 | 行为可对拍、可回滚、schema 不变 |
| 推倒重写 | 乐观 12 个月起 | 无参照物、无法对拍、需重新发现全部隐性规则 |

移植是**机械转换**（有垫片、有对拍）；重写是**重新推导业务**（没有依据）。

### 何况"焕然一新"的部分本来就拿到了

本计划已经包含：新框架、新实时架构（SSE）、新配置体系、新路径基座、
新 API 规范（[13](13-API重新设计.md) 的 R0/R1/R2）、MCP 接入。
**该换的壳全换了，唯独留下最值钱、也最不可再生的那部分 —— 业务规则。**

### 唯一值得局部重写的情况

某个模块**同时**满足：① 逻辑薄；② 现有设计确实有害（不只是难看）；③ 有完整的行为共识。
按上表，本项目里只有 `public_api` 勉强符合 —— 而它只有 6 个路由，重写与否无关大局。

> 结论：**继续按"移植 + 规范化"走。** 想重写的冲动应当导向 [13](13-API重新设计.md)
> 的 R0/R1/R2，那里才是真正该改的地方。

## 7. 铁律

1. **新栈每天必须能在 dev 域名跑起来。**
2. **SSE 端点一律 `async def` 且零阻塞调用**；其余路由一律 `def`（跑线程池）。
   写反了 = 卡死整个 worker。这是 code review 头号检查项。
3. **不许顺手重构业务逻辑。** 搬迁只做机械转换 + 框架适配；烂代码记 TODO，切换后再说。
4. **模型层（`models/`）不动。** 靠 [04](04-兼容层设计.md) 的 db 垫片，2,500 个调用点零改动。
   模型不动 → 数据库 schema 不动 → **回滚时数据绝对安全**。
5. **每搬完一个模块，dev 域名上立刻走查该模块的主要页面。**

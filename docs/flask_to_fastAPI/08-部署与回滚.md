# 08 · 部署与回滚（停机切换）

## 1. 目标形态

```
                          现在                                   切换后
 xinya_flask.service   gunicorn -w 4 wsgi:app :5006     →   gunicorn -k uvicorn.workers.UvicornWorker
 xinya_socket.service  gunicorn eventlet -w 1 :8000     →   ❌ 删除
 nginx /socket.io/     → :8000                          →   ❌ 删除
 nginx /{project}/     —                                →   新增（多项目路径）
 nginx HTTP/2          ?                                →   ★ 必须开
```

**两个进程变一个。**

## 2. 新的 systemd unit

```ini
[Unit]
Description=Xinya FastAPI Service
After=network.target redis-server.service
Requires=redis-server.service

[Service]
User=yukang
Group=www-data
WorkingDirectory=/srv/flaskapp/xinya
Environment="PATH=/srv/flaskapp/xinya/venv/bin:/usr/local/bin:/usr/bin:/bin"
ExecStart=/srv/flaskapp/xinya/venv/bin/gunicorn \
    -k uvicorn.workers.UvicornWorker -w 4 \
    -b 127.0.0.1:5006 \
    --timeout 600 \
    --graceful-timeout 30 \
    asgi:app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

⚠️ **`--timeout` 与 SSE**：长连接不能被当成"卡死的请求"杀掉。上线前用一条挂机
30 分钟的 SSE 连接实测确认不被掐断。必要时改用 uvicorn 直起（不经 gunicorn）。

⚠️ **worker 数 × 线程池 = DB 连接上限**：4 worker × 默认线程池 40 = 160 个潜在连接。
必须核对 MySQL `max_connections` 并显式设 `pool_size` / `max_overflow`。

## 3. nginx 关键改动

```nginx
server {
    listen 443 ssl;
    http2 on;                          # ★ SSE 的生命线，见 12 文档坑 1
    server_name utbabuddha.com v2.utbabuddha.com utba.my;

    location ~ /realtime$ {            # ★ SSE 专用，一条管全部
        proxy_pass http://127.0.0.1:5006;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_set_header X-Forwarded-Prefix /xinya;
        proxy_set_header Host $host;
    }

    location /xinya/ {
        proxy_pass http://127.0.0.1:5006/;
        proxy_set_header X-Forwarded-Prefix /xinya;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Host $host;
        client_max_body_size 50000M;
    }

    # ❌ 删除 location /socket.io/
    # /media_file/ 与 /cctv_authz 保持，注意跟着加前缀
}
```

## 4. 切换流程（停机窗口）

**预计窗口：30–60 分钟**（含冒烟；演练时实测并据此调整公告时间）

### T-14 天
- [ ] APK 版本门禁过渡版已发布，盯升级率
- [ ] dev 环境新栈连续可用 ≥ 1 周
- [ ] 阶段 4 全部验收通过

### T-1 天
- [ ] 公告停机窗口（网页横幅 + 群通知）
- [ ] 代码打 tag `pre-fastapi`，确认可一键 checkout
- [ ] 演练过的切换脚本就位

### T 时刻
```
1. 停机公告页上线（nginx 返回维护页）
2. systemctl stop xinya_flask xinya_socket
3. ★ 数据库全量备份（mysqldump），确认备份文件大小合理
4. git checkout <新版本> && pip install -r requirements.txt
5. alembic upgrade head        # 本次迁移不改 schema，应为 no-op，确认一下
6. cd frontend && npx vite build
7. systemctl daemon-reload && systemctl start xinya_flask
8. 冒烟：/healthz → 登录 → 一个 SSE 页面 → 一次上传 → 一个公开页
9. nginx -t && systemctl reload nginx（切到新 location）
10. 撤下维护页
11. systemctl disable xinya_socket   # 不删，留一周
```

### T+48 小时
- [ ] 盯错误日志、SSE 连接数、内存增长、MySQL 连接数
- [ ] 盯 APK 用户反馈（版本门禁是否漏了谁）

### T+7 天
- [ ] 删除 `xinya_socket.service`
- [ ] 删除旧代码目录备份

## 5. 回滚

**数据安全的根基：本次迁移不改数据库 schema**（模型层靠垫片零改动）。
所以回滚 = 换回代码 + 换回 nginx，**数据完全不受影响**。

```
1. systemctl stop xinya_flask
2. git checkout pre-fastapi && pip install -r requirements.txt
3. cd frontend && npx vite build          # 前端也要回滚（SSE 客户端换回 socket.io）
4. systemctl start xinya_flask xinya_socket
5. nginx 换回旧 location（含 /socket.io/）并 reload
```

**目标：15 分钟内完成。必须在阶段 4 演练过并计时。**

⚠️ 回滚后**已更新 APK 的用户会打不到新接口** —— 因为新 APK 用的是新路径。
所以回滚前要想清楚：APK 是否也要回滚发版。这是"一步到位"方案的固有代价，
也是为什么阶段 4 的验收不能走过场。

## 6. 部署脚本

`devSetup.sh` 生产分支同步更新（`systemctl restart xinya_flask` 名字不变，内容已是 uvicorn），
并加启动自检：

```bash
sudo systemctl restart xinya_flask
sleep 3
curl -fsS http://127.0.0.1:5006/healthz > /dev/null || {
    echo "❌ 启动自检失败"; exit 1;
}
```

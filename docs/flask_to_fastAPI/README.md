# Flask → FastAPI 迁移计划

把 `xinya` 后端从 Flask 一次性重写到 FastAPI，**全面下线 Socket.IO 改用 SSE**，
并顺带完成配置中心与多项目路径基座。

> 盘点日期：2026-09-23（数字见 [01-现状盘点.md](01-现状盘点.md)）
> 方案形态：**一步到位 + 停机切换，不保留任何 Flask**（前提见 [03](03-迁移策略.md) §0）
> 决策全部记录在 [09-决策记录.md](09-待决事项.md)

## 先读这五句话

1. **动机是 SSE，这让 FastAPI 成为对的选择。** WSGI 下一条长连接占住一个 worker，
   做 SSE 只能靠 eventlet 猴子补丁（就是现在 socket.io 那个进程）；ASGI 下一条连接
   只是一个 asyncio 任务。**进程会从 2 个变 1 个。**
2. **这不是"socket.io 换成 SSE"，是拆成两半。** SSE 只能服务器→客户端，
   现有 35 个事件里有 **22 个是客户端→服务器**（抢答、评分、主持人控制），
   必须改成 POST。实时订阅统一到 `{BASE}/api/{app}/realtime`。
3. **一步到位意味着做完之前什么都不能上线。** 唯一的缓解是 dev 域名
   （`yukang.utbabuddha.com`）**从第一天起每天跑新栈**，连续两天起不来就是红灯。
4. **模型层不动。** 靠 db 垫片让 2,500 个调用点零改动 → 数据库 schema 不变
   → **回滚时数据绝对安全**。
5. **切换前必须先给 APK 加最低版本门禁**（[03](03-迁移策略.md) §6）。
   现在 APK 没有版本校验，停机切换后旧版本会直接白屏，用户只会以为"系统坏了"。

## API 重复度评估结论（[13](13-API重新设计.md)）

574 条 URL 其实只有 **505 个处理函数**，69 条是同函数挂多 URL 的兼容别名。
真正的问题**不是"逻辑抄了很多遍"，而是"同一件事有很多种叫法"**：

- 37% 的路径带动词；「读取」有 `get/list/all/detail/info/search/query/read` 八种叫法
- 43% 是纯 POST，其中 **60 条语义错配**（30 个其实是更新、18 个删除、12 个读取）
- 响应信封 **3 种并存** → 前端写了 **21 个** `parseJson`
- GET 接口只有 **5%** 做了分页

建议：**R0 删别名 + R1 统一信封 + R2 统一分页**跟迁移一起做（边搬边规范，几乎不加成本）；
**R3 全面 REST 化不要做** —— 给 505 个接口换名字对用户零价值、风险却是全量的。

## 三条最容易要命的坑

1. **`scoped_session` 在线程池里串场** —— 同步路由跑线程池，线程复用会让 A 请求看见
   B 的未提交数据，**静默出错、把数据写给错的人**。→ [04](04-兼容层设计.md) §1
2. **浏览器每域名 6 连接上限** —— 一条 SSE 永久占一个，开几个标签页后 API 请求开始
   排队，表现为"页面莫名卡住"。**必须开 HTTP/2**。→ [12](12-SSE改造方案.md) §5
3. **nginx 缓冲吃掉 SSE** —— 默认 `proxy_buffering on` 会把消息攒着，
   表现为"延迟几十秒"或"一次涌一堆"。→ [12](12-SSE改造方案.md) §5

# 抢答器设计稿

## 目标

在 `转盘 > 抢答活动` 里做一个现场抢答系统：

- 电脑端作为主持屏，进入后是主页，显示当前题目、答案选项、抢答状态和最终抢答结果。
- 右上角有 setting icon，点击进入配置界面。
- 游客通过入口 URL 或二维码进入游客抢答界面。
- 主持屏和游客端都通过 Socket.IO 连接同一个抢答房间。
- 系统按统一世界时间（UTC epoch milliseconds）开放抢答。
- 只有一个游客可以抢答成功；第一个有效点击会让服务器锁定结果，并广播给主持屏和所有游客端。
- 抢答活动固定为单题模式，一次活动只配置一道题。
- 正确答案需要主持人预设；抢答结果需要显示游客抢到的答案和预设正确答案。

## 页面结构

### 1. 抢答活动主页（主持屏）

入口：`/music/turntable` 点击 `抢答活动` 后进入。

要求：

- 隐藏顶部 navbar。
- 页面右上角放 setting icon。
- 主体显示当前题目。
- 显示答案按钮或答案列表，支持 1-9 个答案。
- 显示抢答状态：
  - 未配置
  - 等待开始
  - 倒计时中
  - 抢答开放
  - 已抢答
  - 已关闭
- 显示最终抢答结果：
  - 抢答人名称
  - 点击的答案编号和答案内容
  - 预设正确答案编号和答案内容
  - 是否答对
  - 服务器判定时间 `server_received_at_ms`
  - 距离开放时间的毫秒差
- 有返回按钮，回到 `抢答活动 / 转盘活动` 两个大按钮页。

### 2. 设置界面

从主持屏右上角 setting icon 进入。

配置项：

- 抢答开始时间
  - 使用 UTC epoch milliseconds 作为最终保存值。
  - 前端 UI 按浏览器本地时区显示日期、时间、毫秒输入。
  - 保存时前端把本地时间换算成 UTC epoch milliseconds。
  - 示例：本地时间输入 `2026-07-02 22:30:00.250 +08:00`，保存值为对应 UTC milliseconds。
- 题目
  - 单行或多行文本。
- 答案选项
  - 支持 1-9 个答案。
  - 每个答案包含：
    - 编号：1-9
    - 答案内容
    - 是否启用
  - 必须选择一个启用答案作为预设正确答案。
- 游客入口 URL
  - 显示一个可复制的公开链接。
  - 显示二维码，游客扫码进入。
  - URL 使用 query 参数传 token，例如：`/quiz?token=abc123` 或 `/#/music/turntable/quiz?token=abc123`。
  - token 要简短，保存在 Redis，24 小时过期。

设置界面操作：

- 保存配置
- 发布配置到 Socket 房间
- 重置抢答结果
- 手动关闭抢答
- 返回主持屏

### 3. 游客抢答界面

游客通过二维码 URL 进入。

要求：

- 不显示主站 navbar。
- 首次进入生成或读取本地游客 ID。
- 游客必须输入名称，未输入时不能进入抢答。
- 通过 Socket.IO 加入对应抢答房间。
- 显示题目和答案按钮。
- 在抢答开始时间之前，按钮禁用，显示倒计时。
- 到达统一世界时间后，按钮开放。
- 点击任意答案后，立刻本地禁用按钮并提交 Socket 事件。
- 如果自己抢答成功，显示“抢答成功”。
- 如果别人更快，显示“已被抢答”。

## 时间设计

抢答判定必须以服务器为准，不能只信任游客浏览器时间。

建议规则：

- 后端服务器时间使用 UTC epoch milliseconds：`Date.now()` / Python `time.time_ns() // 1_000_000`。
- 服务器需要保持 NTP/chrony 同步，保证系统时间接近真实世界时间。
- 前端可以做时间同步，只用于 UI 倒计时和按钮开放体验。
- 主持端设置时间时按本地时间展示和输入，保存、传输、判定全部使用 UTC epoch milliseconds。
- 最终抢答成功判定只看服务器接收到答案时的时间和原子锁结果。

### 前端时间同步

游客端和主持屏连接 Socket 后，周期性发送 ping：

```json
{
  "event": "quiz:time:ping",
  "client_sent_at_ms": 1783002599000
}
```

后端返回：

```json
{
  "event": "quiz:time:pong",
  "client_sent_at_ms": 1783002599000,
  "server_now_ms": 1783002599015
}
```

前端估算：

- `round_trip_ms = client_received_at_ms - client_sent_at_ms`
- `estimated_server_now_ms = server_now_ms + round_trip_ms / 2`
- `client_server_offset_ms = estimated_server_now_ms - client_received_at_ms`

按钮开放显示使用：

```ts
estimatedServerNowMs = Date.now() + clientServerOffsetMs
canAnswer = estimatedServerNowMs >= startAtMs && status === "open"
```

注意：这个只用于 UI，不用于最终判定。

## Socket.IO 房间和事件

建议 namespace：`/quiz`。如果后端现有 Socket.IO 不方便新增 namespace，也可以沿用默认 namespace，但事件名前缀保持 `quiz:`。

### 房间

每个抢答活动有一个简短 `room_token`。游客入口 URL 里的 `token` 参数就是这个值，例如 `?token=abc123`。

- 主持屏加入：`quiz:host:join`
- 游客加入：`quiz:guest:join`
- 后端把同一活动的连接放入同一个 Socket room：`quiz:<room_token>`
- Redis 保存 token 映射和活动状态，TTL 24 小时：`quiz:token:<room_token>`。

### Snapshot

任意客户端加入后，后端立即返回当前状态：

```json
{
  "event": "quiz:snapshot",
  "room_token": "abc123",
  "status": "waiting",
  "server_now_ms": 1783002599123,
  "config": {
    "start_at_ms": 1783002600250,
    "question": "今天活动主题是什么？",
    "correct_answer_index": 1,
    "answers": [
      { "index": 1, "text": "佛曲分享会", "enabled": true },
      { "index": 2, "text": "读书会", "enabled": true }
    ]
  },
  "winner": null
}
```

### 主持端事件

保存配置：

```json
{
  "event": "quiz:host:save_config",
  "room_token": "abc123",
  "config": {
    "start_at_ms": 1783002600250,
    "question": "今天活动主题是什么？",
    "correct_answer_index": 1,
    "answers": [
      { "index": 1, "text": "佛曲分享会", "enabled": true },
      { "index": 2, "text": "读书会", "enabled": true }
    ]
  }
}
```

发布状态：

```json
{
  "event": "quiz:host:publish",
  "room_token": "abc123"
}
```

重置结果：

```json
{
  "event": "quiz:host:reset",
  "room_token": "abc123"
}
```

手动关闭：

```json
{
  "event": "quiz:host:close",
  "room_token": "abc123"
}
```

### 游客端事件

加入房间：

```json
{
  "event": "quiz:guest:join",
  "room_token": "abc123",
  "guest_id": "guest_9f48d9",
  "guest_name": "王小明"
}
```

提交答案：

```json
{
  "event": "quiz:guest:answer",
  "room_token": "abc123",
  "guest_id": "guest_9f48d9",
  "guest_name": "王小明",
  "answer_index": 2,
  "client_clicked_at_ms": 1783002600272
}
```

### 后端广播事件

配置更新：

```json
{
  "event": "quiz:config_updated",
  "room_token": "abc123",
  "config": {
    "start_at_ms": 1783002600250,
    "question": "今天活动主题是什么？",
    "correct_answer_index": 1,
    "answers": []
  },
  "server_now_ms": 1783002599200
}
```

抢答开放：

```json
{
  "event": "quiz:opened",
  "room_token": "abc123",
  "opened_at_ms": 1783002600250,
  "server_now_ms": 1783002600251
}
```

抢答成功并关闭：

```json
{
  "event": "quiz:winner",
  "room_token": "abc123",
  "status": "answered",
  "winner": {
    "guest_id": "guest_9f48d9",
    "guest_name": "王小明",
    "answer_index": 2,
    "answer_text": "读书会",
    "correct_answer_index": 1,
    "correct_answer_text": "佛曲分享会",
    "is_correct": false,
    "server_received_at_ms": 1783002600301,
    "delta_from_start_ms": 51
  }
}
```

抢答失败：

```json
{
  "event": "quiz:answer_rejected",
  "reason": "already_answered",
  "winner_guest_id": "guest_9f48d9"
}
```

## 后端判定规则

服务器收到 `quiz:guest:answer` 后按顺序处理：

1. 读取活动配置。
2. 取得服务器当前 UTC milliseconds：`received_at_ms`。
3. 如果没有配置题目或答案，拒绝。
4. 如果 `received_at_ms < start_at_ms`，拒绝，reason=`too_early`。
5. 如果活动已关闭或已有 winner，拒绝，reason=`already_answered`。
6. 检查 `answer_index` 是否在启用答案内。
7. 检查 `correct_answer_index` 是否存在并指向启用答案；如果缺失，拒绝。
8. 使用原子锁抢占 winner：
   - Redis：`SET quiz:<room_token>:winner <payload> NX`
   - 或数据库事务：对 session row 加锁，只有 `winner_id IS NULL` 才写入。
9. 抢锁成功者成为唯一 winner。
10. 根据 `answer_index === correct_answer_index` 计算 `is_correct`。
11. 广播 `quiz:winner` 给主持屏和所有游客端。
12. 所有游客端收到 winner 后禁用按钮。

不要用客户端提交的 `client_clicked_at_ms` 作为唯一判定依据，因为游客可以篡改浏览器时间。这个字段只用于调试和显示参考。

## 数据模型草案

可以先存在 Redis，后续再落数据库。

### QuizSession

- `id`
- `room_token`
- `token_expires_at`
- `status`: `draft | waiting | open | answered | closed`
- `start_at_ms`
- `question`
- `correct_answer_index`
- `answers_json`
- `winner_json`
- `created_by_user_id`
- `created_at`
- `updated_at`

### QuizAnswer

如果不单独建表，可以放在 `answers_json`：

```json
[
  { "index": 1, "text": "答案 A", "enabled": true, "is_correct": true },
  { "index": 2, "text": "答案 B", "enabled": true }
]
```

### QuizAttempt

后续如果要审计每一次点击，再记录：

- `id`
- `room_token`
- `guest_id`
- `guest_name`
- `answer_index`
- `is_correct`
- `client_clicked_at_ms`
- `server_received_at_ms`
- `accepted`
- `reject_reason`

### Redis Token

抢答房间 token 先存在 Redis，24 小时过期：

```text
quiz:token:abc123 -> <quiz_session_json>, EX 86400
quiz:abc123:winner -> <winner_json>, EX 86400
```

规则：

- token 使用短字符串，例如 6 位字母数字：`abc123`。
- 游客 URL 只带 query 参数：`?token=abc123`。
- 后端从 token 查 Redis，如果不存在或已过期，游客端显示“活动已过期或不存在”。
- 重置抢答结果时删除 `quiz:<room_token>:winner`，但不一定重新生成 token。

## 实现阶段

### Phase 1：前端静态流程

- 抢答活动主页。
- setting icon。
- 配置页面表单。
- 游客入口 URL 和二维码占位。
- 游客抢答页面静态 UI。

### Phase 2：HTTP API 和配置保存

- 创建 / 读取 / 保存 quiz session。
- 生成简短 token。
- 返回游客入口 URL。

### Phase 3：Socket.IO 实时连接

- host join。
- guest join。
- snapshot。
- config broadcast。
- time ping/pong。

### Phase 4：抢答判定

- 按 `start_at_ms` 开放。
- 游客提交答案。
- 后端原子锁 winner。
- 广播 winner。
- 主持屏显示抢答结果、预设正确答案和是否答对。
- 所有游客端关闭按钮。

### Phase 5：现场体验增强

- 倒计时动画。
- 抢答成功音效。
- 结果大屏展示。
- 重置本题结果。
- 记录每次抢答日志。

## 已确认决策

- 抢答活动只需要当前一题，不做多题列表。
- 最终答案需要主持人预设，并在结果中显示游客答案、正确答案和是否答对。
- 游客必须输入名称，不能自动跳过。
- 抢答开始时间在前端按本地时间显示和输入，保存时换算成 UTC epoch milliseconds。
- 游客入口使用简短 token，直接放在 URL query 参数：`?token=abc123`。
- token 保存在 Redis，24 小时过期。
